# 模型与调用通道策略 v1

## 目标

在保证多智能体能力的同时，尽量利用已经购买的模型额度，减少额外 API 成本。

## 一、三层分离

### 1. 智能体角色
负责“谁做什么”。

例如：
- 项目协调智能体
- 产品智能体
- 架构智能体
- 开发智能体
- 测试智能体

### 2. 模型路由
负责“这个任务适合用什么能力等级的模型”。

例如：
- 低成本模型
- 强推理模型
- 强代码模型

### 3. 调用通道
负责“通过什么方式调用”。

例如：
- CLI + 套餐登录
- API
- 本地工具
- MCP
- 人工触发的外部智能体

## 二、当前资源策略

### Codex
优先方向：
- 代码实现
- 读仓库
- 修改文件
- 运行测试
- 复杂工程任务

优先研究：
- 通过 CLI 使用 ChatGPT Plus 套餐额度
- 作为开发智能体 / 代码审查智能体的主要执行通道

### DeepSeek API
优先方向：
- 任务分析
- 低成本结构化判断
- 产品/流程分析
- 简单测试总结
- 作为自动编排中可稳定程序调用的模型

### 豆包工作
当前状态：
- 已有基础会员额度
- 需要确认是否存在可用于自动编排的 CLI / API / 工具接口

## 三、路由原则

1. 不因为“模型强”就让它处理所有任务。
2. 代码和复杂工程优先给强代码模型。
3. 简单分类、总结、状态判断优先用低成本模型。
4. 高风险决策不只看模型能力，还必须经过人工决策关口。
5. 如果 CLI 能稳定完成任务，优先 CLI；如果需要后台自动运行，再考虑 API。

## 四、下一步

建立“模型与调用通道矩阵”，逐项确认：
- 是否能自动调用
- 是否消耗套餐额度
- 是否额外收费
- 是否支持结构化输出
- 是否支持文件 / 终端 / Git
- 是否适合被项目协调智能体自动调度
