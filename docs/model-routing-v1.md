# 模型与调用通道策略 v1

## 目标

在保证多智能体能力的同时，尽量利用已经购买的模型额度，减少额外 API 成本。

## 一、三层分离

### 1. 智能体角色
负责“谁做什么”。

例如：
- 项目协调智能体
- 产品智能体
- 架构智能体
- 开发智能体
- 测试智能体

### 2. 模型路由
负责“这个任务适合用什么能力等级的模型”。

例如：
- 低成本模型
- 强推理模型
- 强代码模型

### 3. 调用通道
负责“通过什么方式调用”。

例如：
- CLI + 套餐登录
- API
- 本地工具
- MCP
- 人工触发的外部智能体

## 二、当前资源策略

### Codex
优先方向：
- 代码实现
- 读仓库
- 修改文件
- 运行测试
- 复杂工程任务

优先研究：
- 通过 CLI 使用 ChatGPT Plus 套餐额度
- 作为开发智能体 / 代码审查智能体的主要执行通道

### DeepSeek API
优先方向：
- 任务分析
- 低成本结构化判断
- 产品/流程分析
- 简单测试总结
- 作为自动编排中可稳定程序调用的模型

### 豆包工作
当前状态：
- 已有基础会员额度
- 已确认可以通过 CLI 连接
- 可作为套餐内能力的重要调用通道

优先方向：
- 产品分析
- 文档整理
- 一般任务推理
- 可通过 CLI 自动执行的非高风险任务

后续重点确认：
- CLI 是否支持非交互模式
- CLI 是否支持结构化输出
- CLI 是否能稳定返回退出码
- 是否适合作为编排器自动调用的子进程

## 三、路由原则

1. 不因为“模型强”就让它处理所有任务。
2. 代码和复杂工程优先给强代码模型。
3. 简单分类、总结、状态判断优先用低成本模型。
4. 高风险决策不只看模型能力，还必须经过人工决策关口。
5. 如果 CLI 能稳定完成任务，优先 CLI；如果需要后台自动运行，再考虑 API。

## 四、下一步

建立“模型与调用通道矩阵”，逐项确认：
- 是否能自动调用
- 是否消耗套餐额度
- 是否额外收费
- 是否支持结构化输出
- 是否支持文件 / 终端 / Git
- 是否适合被项目协调智能体自动调度


## 五、当前优先通道排序

### 第一优先：套餐内 CLI
- Codex CLI
- 豆包工作 CLI

用途：
尽量消耗已购买套餐额度，减少新增 API 成本。

### 第二优先：已有 API 余额
- DeepSeek API

用途：
适合需要稳定程序化调用、结构化输出、后台自动执行的任务。

### 第三优先：新增付费 API
只有在前两类通道无法满足时再考虑。

## 六、当前最值得验证的技术问题

不是“哪个模型最强”，而是两个 CLI 能否被我们的项目协调程序稳定自动调用。

需要分别测试：
1. 能否通过命令一次性传入任务
2. 是否支持非交互执行
3. 输出能否被程序读取
4. 成功/失败是否有明确退出状态
5. 是否可以指定工作目录
6. 是否可以安全限制文件和命令权限
7. 是否能连续调用而不需要人工点确认

如果以上条件成立，CLI 就可以真正成为多智能体系统里的“专业智能体执行通道”。
