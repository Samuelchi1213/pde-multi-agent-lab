# FDE Workbench 参考研究与 PDE 延期功能库

> 记录日期：2026-10-08
> 研究对象：https://github.com/gxfde/fde-workbench
> 适用项目：PDE 多智能体控制台（本仓库）
> 决策状态：**方案已保存，未经逐项批准不启动开发**
> 原则：优先可靠性、可恢复性与安全发布；长期优势先归档，需求真正出现时再评估。
> 本文属于设计参考及待办池，不表示 PDE 已实现表内功能。

## 一、为何参考 FDE Workbench

FDE Workbench v0.1.0 是针对 FDE 团队的项目/任务/调研/交付协作平台；核心技术为 Electron + React + TypeScript 桌面端、Flask API、MySQL、Redis、worker 和 scheduler。
它**不是**开箱即用的“多智能体自动写代码工作台”。其价值在工程组织方式，尤其是后台任务记录、可查询的 AI 执行事件、能力权限、人工审批、业务对象分层与测试。
官方 README 说明 Windows x64 构建配置存在但尚未完成完整发行验收，且开源项目未宣称完成全面安全审计。

与现有 PDE 的差异：
- FDE 强在项目管理、协作管理、细粒度权限、文档和扩展集成。
- PDE 强在自然语言任务 → 动态分工 → Codex/DeepSeek → 独立测试 → 安全发布 → 用户验收 → 定向返工。
- PDE 当前主要单机、单使用者、Windows、本地浏览器入口；不应为了模仿 FDE 引入企业级依赖。

## 二、P0：近期优先开发（先保证可靠，不盲目扩功能）

| ID | 主题 | 从 FDE 借鉴什么 | PDE 要实现的最小结果 / 验收口径 |
|---|---|---|---|
| CORE-01 | 持久化任务状态机 | 独立任务记录、终态、防重复和 worker 语义 | 每次任务/角色/步骤都有 ID 和终态；页面刷新/控制台重启后不会假显示“运行中”；只读检查能识别后台是否存活 |
| CORE-02 | 分步骤恢复和幂等调用 | 任务租约、幂等键、不可重复执行不确定写操作 | 完成的步骤不重跑 Codex/DeepSeek；中断仅继续未完成阶段；同一任务重复点击不会启动第二个线程或覆盖 workspace |
| CORE-03 | 实时进度与诊断 | AI 执行 ID、stage、事件流、持续查询 | Codex 等待中可查看最后心跳、已执行时长、日志；区分运行中/等待批准/已失败/结果未知；不靠大 JSON 猜测 |
| CORE-04 | 预算与结果持久化 | 明确的状态/事件与审批关口 | 模型调用返回即保存响应和 usage；预算不足只阻止**下一次**未经授权调用；审批后继续原任务，不从头开始 |
| CORE-05 | 返工—验收闭环 | 审批事件和状态流转 | QA 失败/人工退回直接生成差异返工任务；保留测试证据与历史；定向修改后回归测试、差异预览、安全发布、二次人工验收均可追踪 |
| CORE-06 | 安全交付审计 | 敏感操作审批和追加式审计事件 | 发布前差异预览和备份；禁止覆盖用户数据；写入前后记录来源版本、操作者、文件清单、结果；失败可回滚和诊断 |

**硬性完成标准（逐项验证）**
1. 人为杀掉运行中的控制台，再启动：已做完的 AI 调用和测试不能被自动重复计费。
2. 长时间 Codex 运行时，页面能显示“后台实际运行/最后日志时间/超时信息”，而不是只显示“执行中”。
3. 用户不批准新预算时，既有代码、日志、回复和任务状态可读取；批准后真正续跑而非重新开始。
4. 老项目数据（包括 src/data 下 JSON 学生数据）不因发布/返工被修改或删除，程序文件支持差异备份和回滚。
5. 人工退回后不生成新的全团队任务；单独修复后测试证据和验收结论归入原任务历史。

**实施建议**：先做一个单机可靠任务引擎；可优先采用 Python + SQLite（评估后决定），以事务/唯一约束实现状态一致性。不要立刻安装 Redis/MySQL。把控制台业务接口与任务执行逻辑分开，不一次性重写整个 Web 界面。

## 三、P1：P0 稳定后按需开发（先入候选池）

| ID | 候选优势 | 延后原因 | 启动条件 | 最小可行版本 |
|---|---|---|---|---|
| NEXT-01 | 统一的 Codex/DeepSeek/其他模型适配器 | 当前有可运行的两类执行器，重构有风险 | P0 的状态机和预算恢复稳定，需要引入第二套可自动执行的模型通道 | 同一 Task/Result/Usage/Error 契约，二者均保留可替换 |
| NEXT-02 | 简洁任务中心与历史列表 | 单任务先要可靠，不能 UI 先行 | 同时维护多个历史开发任务，查找/恢复费劲 | 最近任务、运行中、待审批、失败、已验收四个分组，状态按真实任务存储 |
| NEXT-03 | 测试结果与交付证据界面 | 目前依赖 JSON 日志和截图 | 连续两轮人工验收中出现证据查找困难 | 每项测试、变更、风险、历史验收有独立详情页 |
| NEXT-04 | 分角色成本与执行器策略 | 深度调度不成熟易扩大成本 | P0 usage 精确存储，实际反复需要优化成本 | 每轮每角色 token、耗时、预算、手动批准续跑 |
| NEXT-05 | 可复用 Skills / 工作流模板 | 需要多次稳定实践才能抽象 | 同一类开发/测试/发布流程被验证重复使用 3 次以上 | 版本化、可禁用的本地模板，不直接执行未审查脚本 |

## 四、PARKED：暂不着急的好点子（保留，条件触发后再评估）

| ID | 从 FDE 借鉴的优势 | 为什么暂缓 | 何时重新评估 |
|---|---|---|---|
| LATER-01 | 多项目工作台 / 项目组合视图 | 先解决单任务可靠性 | PDE 同时管理 3 个及以上真实项目且需要跨项目概览 |
| LATER-02 | 看板、甘特图、任务依赖和负责人 | 当前个人独立使用，复杂看板容易成为负担 | 多阶段依赖明显、真实任务积压，或两人以上协作 |
| LATER-03 | 项目成员管理和正式账号/RBAC | 当前本地演示角色不是真实身份认证 | 开始多人共享控制台或外网访问前，必须专项设计 |
| LATER-04 | 文档模板、交付文件版本、文件预览 | 目前以代码差异+测试证据为核心 | 一项目需交付多版文档/附件，并经常追溯变化 |
| LATER-05 | 调研、需求访谈、AI 机会发现和方案设计模块 | 不属于当前 PDE 自动开发闭环 | 出现明确的售前/调研/需求管理实际项目 |
| LATER-06 | Skills 市场 / 插件市场 / 第三方扩展 | 扩展能力与安全风险同时增加 | 核心工作流稳定，确实有 3 个以上可复用、安全审查通过的扩展 |
| LATER-07 | 微信/ClawBot/远程通知与外部入口 | 引入外部权限、隐私和持续运维 | 经常不在电脑旁仍要审批，且已解决账号权限和安全鉴权 |
| LATER-08 | 企业级 MySQL + Redis + 独立 worker/scheduler | 安装维护复杂；单机 Windows 不划算 | 本地 SQLite/单 worker 无法满足并发、跨机器任务或恢复要求，有实测瓶颈 |
| LATER-09 | Electron 桌面客户端与安装包 | 现有本地浏览器+静默启动足够 | 浏览器控制台显著限制操作，或需要面向其他用户稳定分发；先做 Windows 发行验收 |
| LATER-10 | 对象存储、病毒扫描、批量文件处理 | 重型依赖并增加数据面 | 需要安全处理大量外部用户上传文件时 |
| LATER-11 | 多种 AI 模型偏好、路由和策略管理 | 当前 DeepSeek/Codex 使用逻辑清晰 | 多个可替代供应商真实投入使用，需要按任务选型 |
| LATER-12 | 团队级审计中心、管理后台和统计大屏 | 单人本地使用过度设计 | 有团队合规、追责审计、跨项目权限管理需求 |
| LATER-13 | 自动更新/发布管线的专业化 | 已有一键更新；先确保更新不中断任务 | 用户实际多次因更新损失任务状态，或开始对外发版 |

**延期管理规则：**
- PARKED **不是拒绝，也不是承诺开发**。新需求要先验证真实使用痛点，复查当前维护成本，再确认范围。
- 每次审视只选择与当下任务直接相关的 1–2 项；不得一次性“全套移植 FDE”。
- 从 PARKED 升级为 P1/P0，必须补上：具体问题、收益、先决条件、测试/验收标准、风险和使用成本。
- 安全、数据和身份验证一旦成为上线前置要求，不受优先级表限制，必须先解决。

## 五、明确暂不照搬的技术方案

- **不立即重写成 Electron + React + Flask + MySQL + Redis 全家桶**：会显著增加当前 Windows 本地使用和维护复杂度。
- **不把 FDE 的 Redis 短时 AI 执行当成可靠断点续跑**：源码中的短时 AI execution 默认 TTL 3600 秒；应借鉴其更持久的 BackgroundJob/worker 设计思想。
- **不直接复制 FDE 的权限/模型服务代码**：其团队场景、认证和外部 DSH 运行时，与 PDE 的本地 Codex/DeepSeek 结构不同。
- **不照搬扩展市场或 AI 自动高权限操作**：任何发布、删除、外发、支付/预算扩展仍须明确确认。
- **不默认商用/生产级成熟度**：FDE 的 README 明示其安全审计和 Windows 发行验收边界；借鉴前按需复审。

## 七、下次继续 PDE 时的起点

先阅读此文与 `CURRENT.md`、`TASKS.md`，复核真实代码状态。

建议顺序：
1. 明确 CORE-01/CORE-02 的现有实现、最小状态模型和迁移/回滚方案；
2. 在隔离的测试任务中模拟后台崩溃、控制台重启、重复点击、预算超额；
3. 不影响现有已可用的“辅导员工作台 v2”开发/验收流程；
4. 获得实际 Windows 运行验证后，再进入后续任务；
5. 其余“好点子”继续停在 PARKED，除非用户明确同意启动。
