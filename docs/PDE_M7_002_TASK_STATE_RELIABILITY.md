# PDE Milestone 7.002｜任务状态一致性与中断诊断（第一阶段）

> 开始时间：2026-10-08
> 状态：**代码已提交；离线状态单元测试通过；Windows 本机尚待操作验证**
> 参考路线：[FDE Workbench 工程参考与延期功能库](FDE_WORKBENCH_LESSONS_AND_BACKLOG.md)

## 本轮目标

解决同一任务出现“后台实际已结束、浏览器还显示执行中”的问题，并降低在状态写入时进程终止导致的文件损坏风险。

**本轮只做到任务记录可靠保存与如实展示中断，不做模型 API 的自动断点续跑。**

## 已改动的文件及责任

- `web_console_v1/task_state.py`：共享只读任务状态投影、活动状态/中断判定、原子 JSON 写入及损坏提示。
- `web_console_v1/test_task_state.py`：13 项离线单元回归测试，不调用 DeepSeek/Codex。
- `web_console_v1/app.py`：
  - `/api/team/status` 和 `/api/team/resume` 使用同一状态读取逻辑；
  - 控制台重启只读取已保存的任务，不因为状态停在“执行中”而自动重复执行；
  - 已异常退出的线程（即使旧内存 running 标志未清零）被识别为中断；
  - 人工验收、预算审批、候选发布、定向返工等 state.json 保存改用原子替换；
  - 开发 / 诊断工具中新增“验证任务状态恢复（离线）”按钮与对应只读自检接口。
- `web_console_v1/team_executor.py`：团队阶段事件和状态写入改为原子替换。
- `web_console_v1/manual_rework.py`、`web_console_v1/qa_recovery.py`：复用相同的 JSON 原子保存方式。

## 测试覆盖

13 项离线用例覆盖：
- JSON 状态原子保存、中文和历史字段完整性；
- JSON 无法序列化时，已有状态不丢失；
- 后台线程仍存在时优先展示最新磁盘进度；
- 线程意外退出/控制台重启后，原“执行中”显示为“执行中断”，原始 state.json 不修改；
- 线程已终止，但内存 running 标志未清零时正确识别；
- QA 恢复中断与定向返工中断分别保留原始凭据，不自动二次付费；
- 预算待批准、候选待验收等状态不误标为失败；
- 内存最终异常和磁盘旧进度之间的冲突解决；
- 损坏的 state.json 被明确报告，绝不静默当作成功；
- 不存在的状态文件不得显示为成功。

测试命令（仅供维护者参考）：
```text
python -m unittest discover -s web_console_v1 -p test_task_state.py -v
```
2026-10-08 在独立 Python 3.13 离线环境对同一测试逻辑进行了运行，13 项通过；GitHub 上的变更仍需在用户的 Windows 环境运行自检按钮确认。

## 本机人工验收（不需要终端）

1. 确保没有 Codex 或 DeepSeek 团队任务正在执行，然后通过 PDE“检查更新 → 立即更新”更新源码，再退出并静默启动控制台。
2. 展开“开发 / 诊断工具”，点击“验证任务状态恢复（离线）”。
3. 应看到 `13` 项测试、退出码 `0`、状态自检通过。
4. 关闭当前控制台后重新启动，进入已有任务界面，确认历史任务仍可恢复显示，且不会自行启动模型。
5. 原“已完成”“等待人工验收”“需要人工返工”应保持原有结论，不得因本次更新而改变人工验收结果。
6. 不需要在真实工作台创建新学生记录；不要为验证“中断”主动关闭正在付费执行的任务。

## 未完成 / 明确留待下一阶段

- **真正的步骤级续跑和幂等外部调用：未实现。** 目前只标记中断，恢复下一次 Codex/DeepSeek 调用前仍要专门设计检查点和审批机制。
- 持久任务引擎 / SQLite 迁移 / 多任务租约：未实现，不在本轮范围。
- Codex 运行过程中的实时 stdout/progress：未实现，后续 M7-004。
- DeepSeek 超预算时严格从原调用点继续：未实现，后续 M7-005。
- 多线程同时更新**同一个**任务状态文件的冲突需要单独设计锁和版本控制；本轮改为原子替换并不等于事务协调。
- 原有 `sync_allowed_paths` 目录覆盖风险仍属于历史代码路径，实际发布应优先走现有“文件差异预览 + 确认 + 备份”的安全发布接口，后续需要进一步清理遗留直写路径。

## 风险边界

- 不主动调用模型、不同步任何真实项目代码和学生数据。
- 更新前应等待当前正在运行的付费任务完成；新版本不会“魔法般”接管旧进程。
- 本次变更的验收依据是离线测试与 Windows 本机人工检查，不能把静态代码检查当作生产稳定性证明。
